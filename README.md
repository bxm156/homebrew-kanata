# kanata-launch

A tiny macOS launcher for [kanata](https://github.com/jtroo/kanata) that holds the Input Monitoring and Accessibility grants itself, so that:

- upgrading kanata does not require re-granting permissions,
- kanata can run inside tmux without giving tmux keyboard access, and
- only a kanata binary built and signed by this repository's CI is ever started.

The repository has three parts:

| Part | What it is |
| --- | --- |
| `kanata-launch.c`, `Makefile` | The launcher, built locally |
| `.github/workflows/build-kanata.yml` | Builds kanata from an upstream tag, signs it, publishes a release |
| `Formula/kanata.rb` | Homebrew formula that installs that signed build (generated by the workflow) |

## Direction change (in progress)

The plan is now to drop the launcher and rely on kanata's own signature instead:

- The workflow signs every kanata build with the same self-signed certificate and the same identifier. macOS ties the privacy grant for a certificate-signed binary to that pair, not to one build, so the grant should carry over between versions and a binary signed by anything else should not get it.
- The formula copies the signed binary to `$(brew --prefix)/var/kanata/kanata-signed`, a path that does not change between versions, because macOS also ties the grant to the binary's real path.
- kanata is run directly from that path and granted Input Monitoring and Accessibility once.

State of that work:

- The workflow and formula are in place, and `kanata-v1.12.0` is signed this way.
- **Not yet verified:** that the grant survives an upgrade.
- The launcher described below is no longer needed for this and will be removed once the new approach is verified. Without it, kanata started inside tmux is attributed to tmux again.

## Status

Experimental.

- **Verified:** under both launchd and tmux, macOS evaluates kanata's Input Monitoring check against `kanata-launch` (confirmed in the `tccd` log on macOS 27 with kanata 1.12.0).
- **Verified:** the launcher refuses a kanata binary that is not signed by the expected certificate.
- **Not yet verified:** kanata actually grabbing the keyboard once `kanata-launch` has been granted the permissions.

## The problem

macOS does not check keyboard permissions against the process that asks for access. It checks that process's *responsible process*, which is normally inherited from whatever started it.

| How kanata is started | Responsible process | Consequence |
| --- | --- | --- |
| launchd → sudo → kanata | kanata itself | The grant is tied to the versioned Homebrew binary, so every upgrade needs a re-grant |
| tmux → sudo → kanata | tmux | Fails unless tmux is granted keyboard access |
| anything → sudo → kanata-launch → kanata | kanata-launch | One grant, on a binary that rarely changes |

## How the launcher works

1. **Stage 1.** `kanata-launch` re-execs itself with the "disclaim responsibility" spawn attribute. That makes it its own responsible process regardless of who started it.
2. **Stage 2.** It verifies kanata (below), starts it as a normal child process, and stays alive. kanata inherits `kanata-launch` as its responsible process, so the privacy checks land on the launcher.

It forwards `SIGTERM`, `SIGINT` and `SIGHUP` to kanata and exits with kanata's exit status, so launchd `KeepAlive` and restarts behave as they would with kanata alone.

## Making sure it only runs the real kanata

Moving the grant onto the launcher means whatever the launcher starts gets keyboard access. Homebrew's own kanata is ad-hoc signed, which identifies nothing, and lives in a directory your user can write to. So the launcher checks before it runs anything:

1. It copies the kanata binary into a root-only directory (`/var/db/kanata-launch`) and works on that copy, so the file cannot be swapped between the check and the exec.
2. It requires the copy to have an intact code signature with a specific identifier, made by a specific certificate:

   ```text
   identifier "com.bryanmarty.kanata" and certificate leaf = H"<hash of signing/kanata-signing-cert.pem>"
   ```

3. It starts kanata with a fixed, minimal environment.

The signing key exists only as a GitHub Actions secret in this repository. The workflow builds kanata from an upstream tag and signs it, so every new version passes the check with no step on your Mac, and nothing running on your Mac can sign a replacement.

What the signature proves is "this repository's workflow built it", not "the source is benign". The workflow is manual-trigger only, so you decide which upstream version gets signed.

## Setup

Requires an Apple silicon Mac and the Xcode command line tools.

### 1. Install the signed kanata

```sh
brew tap bxm156/kanata-launch https://github.com/bxm156/kanata-launch
brew uninstall kanata            # if the Homebrew core version is installed
brew install bxm156/kanata-launch/kanata
```

### 2. Build the launcher

```sh
make
make check    # confirms the installed kanata carries the expected signature
```

The kanata path and config path are compiled in. Override the defaults if yours differ:

```sh
make KANATA_BIN=/opt/homebrew/bin/kanata KANATA_CFG="$HOME/.config/kanata/kanata.kbd"
```

Running `./kanata-launch` as a normal user is a safe dry run: it performs the signature check and then stops, because it needs root to start kanata.

### 3. Run it

1. Run `kanata-launch` as root wherever you currently run kanata, for example from the script your LaunchAgent or sudoers rule points at:

   ```sh
   #!/bin/sh
   exec /path/to/kanata-launch
   ```

2. In System Settings → Privacy & Security, enable `kanata-launch` under both **Input Monitoring** and **Accessibility**. Use the `+` button to add the binary if it is not listed.
3. Restart kanata.

`kanata-launch` takes no arguments; anything passed to it is ignored.

## Upgrading kanata

1. Run the **Build and sign kanata** workflow with the new version:

   ```sh
   gh workflow run build-kanata.yml -R bxm156/kanata-launch -f version=1.13.0
   ```

2. When it finishes, `brew update && brew upgrade kanata`, then restart kanata.

No permissions need re-granting and the launcher does not need rebuilding.

## Using your own fork

The certificate here belongs to this repository. To run your own copy:

1. Create a self-signed code-signing certificate and export it as a `.p12`.
2. Commit the public certificate as `signing/kanata-signing-cert.pem`.
3. Store the `.p12` (base64) and its password as the repository secrets `SIGNING_P12_BASE64` and `SIGNING_P12_PASSWORD`.
4. Change the identifier in the `Makefile` (`KANATA_SIGN_ID`) and the workflow (`SIGN_IDENTIFIER`) to your own; they must match.

## Checking which process macOS blames

```sh
/usr/bin/log show --info --last 1m --predicate 'process == "tccd"' \
  | grep -E 'Handling access request|responsible=' | grep -i kanata
```

Look for `Sub:{...}` and `responsible_path=`. They should name `kanata-launch`.

## Caveats

- **Private API.** `responsibility_spawnattrs_setdisclaim` is an undocumented libSystem function. It has been stable for years but could change in a macOS update.
- **Rebuilding or moving the launcher invalidates the grant.** The grant is tied to the launcher's path and code hash (it is ad-hoc signed). Re-grant after either.
- **The launcher itself is user-writable** unless you install it somewhere root-owned. Replacing it loses the keyboard grant, but if a passwordless sudo rule points at it or at a script that runs it, anything running as your user can still get root through that rule. The signature check protects the keyboard grant, not root.
- **The config file is not verified.** Whatever is at the compiled-in config path is what kanata loads.
- **The GitHub repository is part of the trust chain.** Anyone who can run the workflow or read its secrets can produce a binary the launcher accepts.
- **The certificate expires** (see `openssl x509 -in signing/kanata-signing-cert.pem -noout -enddate`). Replacing it means rebuilding the launcher and re-granting.
- **macOS only**, Apple silicon only as built here.
